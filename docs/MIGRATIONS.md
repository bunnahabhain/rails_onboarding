# Database Migrations Guide

This document describes the database migrations for the Rails Onboarding gem, their dependencies, execution order, and rollback procedures.

## Overview

The Rails Onboarding gem provides several migration templates that add the necessary database schema to support onboarding functionality in your Rails application. All migrations are designed to be safely reversible with proper rollback support.

## Migration Files

### 1. `add_onboarding_users.rb` - Core Onboarding Fields

**Purpose**: Adds the primary onboarding tracking columns to the User model.

**Columns Added**:
- `onboarding_completed` (boolean) - Whether user has completed onboarding
- `onboarding_completed_at` (datetime) - When onboarding was completed
- `onboarding_current_step` (string) - Current step in the onboarding flow
- `onboarding_skipped` (boolean) - Whether user skipped onboarding
- `feature_tooltips_shown` (jsonb/json/text) - Tracks which tooltips have been shown

**Indexes Added**:
- Single column: `onboarding_completed`, `onboarding_current_step`
- Composite: `[onboarding_completed, created_at]` - For finding users needing onboarding

**Database Adapter Support**:
- PostgreSQL/PostGIS: Uses `jsonb` for `feature_tooltips_shown` (optimal)
- MySQL2/Trilogy/MySQL: Uses `json` for `feature_tooltips_shown`
- SQLite and others: Uses `text` for `feature_tooltips_shown` (requires serialization)

**Dependencies**: None - This is the base migration

**Generated by**: `rails generate rails_onboarding:install`

### 2. `add_milestone_tracking_to_users.rb` - Milestone System

**Purpose**: Adds fields to track user achievements and milestone progress.

**Columns Added**:
- `milestones_achieved` (text) - JSON array of achieved milestone keys
- `milestone_points` (integer) - Total points accumulated from milestones
- `last_milestone_at` (datetime) - When the last milestone was achieved

**Indexes Added**:
- Single column: `milestone_points`, `last_milestone_at`

**Dependencies**:
- Requires `add_onboarding_users.rb` to be run first (depends on User table modifications)

**Generated by**: `rails generate rails_onboarding:install` (if milestones enabled)

### 3. `add_analytics_to_rails_onboarding.rb` - Analytics Events Table

**Purpose**: Creates a dedicated table for tracking onboarding analytics events.

**Table Created**: `rails_onboarding_analytics_events`

**Columns**:
- `id` (primary key)
- `user_type` (string) - Polymorphic user type
- `user_id` (bigint) - Polymorphic user ID
- `event_type` (string) - Type of event (e.g., 'onboarding_step_started', 'onboarding_step_completed')
- `properties` (text) - Serialized JSON properties
- `session_id` (string) - Browser/user session identifier
- `occurred_at` (datetime) - When the event occurred
- `created_at`, `updated_at` (timestamps)

**Indexes Added**:
- **Single column**: `event_type`, `occurred_at`, `session_id`
- **Polymorphic indexes** (optimized for queries on specific user types):
  - `[user_type, user_id]` - General user lookup
  - `[user_type, user_id, event_type]` - User events by type
  - `[user_type, user_id, occurred_at]` - User events by date
- **Composite indexes** (for common analytics queries):
  - `[event_type, occurred_at]` - Events by type over time
  - `[user_id, session_id]` - User sessions
  - `[session_id, occurred_at]` - Session timeline
  - `[event_type, session_id]` - Event types per session

**Dependencies**: None - Creates new table

**Generated by**: `rails generate rails_onboarding:install` (if analytics enabled)

### 4. `add_robustness_fields_to_users.rb` - Error Recovery

**Purpose**: Adds fields for error tracking and session recovery.

**Columns Added**:
- `onboarding_errors` (text) - Serialized array of error records
- `onboarding_failed_actions` (text) - Serialized array of failed action attempts
- `onboarding_session_data` (text) - Serialized session state for recovery

**Indexes Added**:
- Reuses existing: `onboarding_completed`, `onboarding_current_step`

**Dependencies**:
- Requires `add_onboarding_users.rb` (adds indexes to columns created there)

**Generated by**: `rails generate rails_onboarding:install` (if robustness features enabled)

### 5. `add_onboarding_indexes.rb` - Performance Optimization

**Purpose**: Adds additional indexes for query performance (can be run separately).

**Indexes Added to `users` table**:
- `onboarding_completed`
- `onboarding_current_step`
- `onboarding_skipped`
- `onboarding_completed_at`
- `last_milestone_at`
- `[onboarding_completed, created_at]` (composite)

**Indexes Added to `rails_onboarding_analytics_events` table** (if exists):
- `[user_id, event_type]`
- `[event_type, created_at]`
- `session_id`
- `[user_id, session_id]`

**Safety Features**:
- Checks if indexes already exist before adding
- Checks if tables exist before modifying
- Safe to run multiple times (idempotent)

**Dependencies**:
- Can run after any of the above migrations
- Checks for table/index existence, so order is flexible

**Generated by**: Can be run manually or via install generator

## Recommended Migration Order

When installing the gem, run migrations in this order:

```bash
# 1. Core onboarding fields (REQUIRED)
rails generate rails_onboarding:install
rails db:migrate

# This will run migrations in the following order automatically:
# 1. add_onboarding_users.rb
# 2. add_milestone_tracking_to_users.rb (if enabled)
# 3. add_analytics_to_rails_onboarding.rb (if enabled)
# 4. add_robustness_fields_to_users.rb (if enabled)
# 5. add_onboarding_indexes.rb (performance optimization)
```

## Rollback Procedures

All migrations include proper `down` methods for safe rollback. They follow these best practices:

1. **Remove indexes before columns** - Prevents errors during rollback
2. **Check existence before removal** - Uses `if index_exists?`, `if column_exists?`, `if table_exists?`
3. **Reverse order of operations** - Down method reverses all changes from up method

### Rolling Back Individual Migrations

```bash
# Rollback the last migration
rails db:rollback

# Rollback specific number of migrations
rails db:rollback STEP=3

# Rollback to a specific version
rails db:migrate:down VERSION=20240101120000
```

### Rolling Back All Onboarding Migrations

```bash
# Find the version number of the first onboarding migration
rails db:migrate:status | grep add_onboarding

# Rollback to before that version
rails db:migrate VERSION=<version_before_first_onboarding_migration>
```

### Safe Rollback Example

```ruby
# The down method for add_onboarding_users.rb:
def down
  # 1. Remove indexes first (to avoid errors)
  remove_index :users, name: 'index_users_on_onboarding_status_and_created' if index_exists?(...)
  remove_index :users, :onboarding_current_step if index_exists?(...)
  remove_index :users, :onboarding_completed if index_exists?(...)

  # 2. Remove columns in reverse order
  remove_column :users, :feature_tooltips_shown if column_exists?(...)
  remove_column :users, :onboarding_skipped if column_exists?(...)
  remove_column :users, :onboarding_current_step if column_exists?(...)
  remove_column :users, :onboarding_completed_at if column_exists?(...)
  remove_column :users, :onboarding_completed if column_exists?(...)
end
```

## Database Adapter Compatibility

The migrations are designed to work with multiple database adapters:

### PostgreSQL / PostGIS
- Uses `jsonb` for JSON columns (most efficient)
- Full support for all features
- Recommended for production

### MySQL / MySQL2 / Trilogy
- Uses `json` column type (native JSON support)
- Full support for all features
- Good production option

### SQLite
- Uses `text` columns for JSON data
- Requires application-level serialization
- Suitable for development/testing
- Not recommended for production at scale

### Other Databases
- Falls back to `text` columns with serialization
- May require additional configuration
- Test thoroughly before production use

## Data Retention and Cleanup

Analytics events can accumulate over time. The gem includes automated cleanup:

### Rake Task for Cleanup

```bash
# Clean up old analytics data (based on configuration)
rails rails_onboarding:analytics:cleanup
```

### Configuration

```ruby
# config/initializers/rails_onboarding.rb
RailsOnboarding.configure do |config|
  # Keep analytics data for 90 days
  config.analytics_data_retention_days = 90
end
```

### Scheduled Cleanup

Add to your scheduled jobs (e.g., cron, whenever, sidekiq-cron):

```ruby
# Run cleanup weekly
every :sunday, at: '2am' do
  rake 'rails_onboarding:analytics:cleanup'
end
```

### Manual Archival

Before cleanup, you can export data for archival:

```bash
# Export analytics to CSV
rails rails_onboarding:analytics:export[2024-01-01,2024-12-31,archive.csv]
```

## Index Performance Considerations

### Single Column Indexes

Used for simple queries:
```sql
-- Uses index on onboarding_completed
SELECT * FROM users WHERE onboarding_completed = false;
```

### Composite Indexes

Used for complex queries:
```sql
-- Uses index on [onboarding_completed, created_at]
SELECT * FROM users
WHERE onboarding_completed = false
AND created_at > '2024-01-01'
ORDER BY created_at DESC;
```

### Polymorphic Indexes

Optimized for polymorphic associations:
```sql
-- Uses index on [user_type, user_id, event_type]
SELECT * FROM rails_onboarding_analytics_events
WHERE user_type = 'User'
AND user_id = 123
AND event_type = 'step_completed';
```

## Migration Testing

Before deploying to production:

1. **Test on a staging database** with production-like data
2. **Check migration time** on large datasets
3. **Verify rollback works** without data loss
4. **Test with your database adapter** (PostgreSQL, MySQL, etc.)
5. **Check index creation time** on large tables

### Testing Commands

```bash
# Test migration up
rails db:migrate

# Test migration down (in development)
rails db:rollback

# Check schema
rails db:schema:dump

# Verify indexes
rails db

# In psql/mysql:
\d users  # PostgreSQL
SHOW INDEXES FROM users;  # MySQL
```

## Troubleshooting

### Issue: Migration fails with "column already exists"

**Solution**: The migration includes safety checks, but if you've run partial migrations:

```bash
# Check current schema
rails db:schema:dump

# Remove the problematic migration from schema_migrations
rails db

# In Rails console:
ActiveRecord::Base.connection.execute(
  "DELETE FROM schema_migrations WHERE version = '20240101120000'"
)
```

### Issue: Index already exists

**Solution**: Our migrations check for index existence, but you can manually remove:

```ruby
# In Rails console
ActiveRecord::Migration.remove_index :users, :onboarding_completed if
  ActiveRecord::Migration.index_exists?(:users, :onboarding_completed)
```

### Issue: Slow migration on large table

**Solution**: For tables with millions of rows:

1. Run migrations during low-traffic periods
2. Consider online migration tools (pt-online-schema-change for MySQL)
3. Add indexes concurrently in PostgreSQL:

```ruby
# Custom migration for large PostgreSQL tables
def up
  add_index :users, :onboarding_completed, algorithm: :concurrently
end
```

### Issue: Different JSON column types across databases

**Solution**: Our migrations handle this automatically, but verify:

```ruby
# In Rails console
User.columns_hash['feature_tooltips_shown'].sql_type
# PostgreSQL: "jsonb"
# MySQL: "json"
# SQLite: "text"
```
